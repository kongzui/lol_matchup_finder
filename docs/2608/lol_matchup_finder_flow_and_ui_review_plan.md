# LoL 매치업 도구 전체 흐름·중복 호출·UI 개선 검토서

- 작성일: 2026-08-31
- 검토 범위: 현재 React 화면, FastAPI API, Riot API 호출 경로, SQLite 저장 흐름,
  새로고침·재시작 동작, 기존 문서
- 문서 목적: 구현 순서를 정하는 문서가 아니라, **현재 무엇이 헷갈리고 어떤 상태가 되면 좋은지**를
  오해 없이 설명하는 문서예요.
- 검토 방식: 소스 코드 전체 흐름과 로컬 SQLite의 숫자만 읽기 전용으로 확인했어요.
  실제 Riot API 호출과 브라우저 클릭 테스트는 실행하지 않았어요.

---

## 1. 한 문장 결론

이 프로젝트의 기능을 새로 갈아엎을 필요는 없어요.

가장 큰 문제는 **경기를 가져오는 여러 기능이 사실 같은 일을 하는데도 서로 다른 작업처럼 움직이고,
사용자가 “누구의 데이터를 어디까지 가져왔는지”, “지금도 일하고 있는지”, “새로고침해도 이어지는지”를
한눈에 알 수 없다는 것**이에요.

따라서 다음 세 가지를 중심으로 흐름을 정리하는 것이 좋아요.

1. 한 명 검색, 여러 명 수집, 앱 시작 시 수집을 하나의 `경기 데이터 수집` 흐름으로 묶어요.
2. 모든 긴 작업의 진행 상태와 완료 결과를 한곳에서 보여줘요.
3. `저장된 매치업 조회`와 `Riot에서 새 데이터 가져오기`를 화면과 동작에서 분명히 나눠요.

## 2. 이 프로젝트는 무엇을 위한 도구인가요?

README에 적힌 처음 목적은 특정 유저와 챔피언·라인 조건으로 매치업을 찾고,
상대 Riot ID를 복사해 다른 사이트에서 활용하는 것이에요.

현재 코드는 여기에 관심 유저, 여러 명 수집, 자동 수집, 로컬 DB 조회, 상세 빌드·룬 기능이 더해졌어요.
원래 목적을 포함하면서 현재 기능까지 설명하는 안전한 정의는 다음과 같아요.

> 관심 있는 LoL 유저들의 솔로 랭크 경기를 내 컴퓨터에 모아 두고,
> 특정 챔피언 대 특정 챔피언의 라인 매치업을 빠르게 찾아 복기하거나
> 상대 Riot ID를 다른 사이트에서 활용하는 도구예요.

현재 UI에서 자주 쓰는 사람에게 권장할 수 있는 순서는 아래와 같아요.

```text
관심 유저 등록
→ 그 유저들의 경기 데이터 수집
→ 누구의 데이터가 최신인지 확인
→ 저장된 경기에서 원하는 매치업 조회
→ 경기 상세 확인 또는 상대 Riot ID 복사
```

한 명을 바로 확인하는 `개별 유저 검색`도 원래 목적과 이어지는 중요한 지름길이에요.
모든 사용자가 먼저 관심 유저를 등록하도록 강제하면 안 돼요.
원래 핵심인 **조건에 맞는 상대 찾기와 Riot ID 활용**을 지키면서,
반복 사용에서는 **수집 → 저장 → 조회 → 활용** 흐름이 자연스럽게 이어지게 하는 것이 좋아요.

### 근본을 바꾸지 않기 위해 유지할 것

- React + FastAPI + SQLite로 이루어진 로컬 앱 구조는 유지하는 것이 좋아요.
- 한국 서버와 솔로 랭크에 집중하는 좁은 범위도 유지하는 것이 좋아요.
- Riot에서 받은 원본 경기와 빠른 조회용 인덱스를 나눠 저장하는 방식은 좋아요.
- 같은 경기를 SQLite에 캐시해 Riot API 재호출을 줄이는 방향도 맞아요.
- 관심 유저를 DB 조회의 기본 대상으로 쓰는 흐름은 편리해요.
- 탭을 바꿔도 진행 중 화면을 없애지 않아 작업이 계속 보이는 현재 장점은 유지해야 해요.
- 경기 카드, 룬·아이템·빌드 상세, Riot ID 복사, OP.GG 연결도 프로젝트 본질에 잘 맞아요.
- 기존 사용자를 위해 `저장된 매치업 조회`를 기본 화면으로 두는 것도 괜찮아요.

즉, 새 앱을 만드는 것이 아니라 **현재 기능 사이의 길을 정리하는 작업**이 필요해요.

## 3. 먼저 용어부터 하나로 맞추는 것이 좋아요

현재는 같은 기능이 화면과 코드에서 여러 이름으로 불려요.

| 현재 섞여 있는 표현 | 권장 표현 | 쉬운 뜻 |
| --- | --- | --- |
| 메모 유저, 메모된 유저, 관심 유저 | 관심 유저 | 자주 살펴볼 사람 |
| 유저 매치 수집, multi search, 자동 매치 수집 | 경기 데이터 수집 | Riot에서 새 경기를 가져와 저장하는 일 |
| 앱 시작 시 수집, auto refresh | 앱 시작 시 자동 수집 | 프로그램을 켤 때 관심 유저를 확인하는 일 |
| DB 조회 | 저장된 매치업 조회 | 이미 내 컴퓨터에 있는 경기에서 찾는 일 |
| Data Dragon 갱신 | 게임 정보 갱신 | 챔피언·룬·주문 그림과 이름을 최신으로 맞추는 일 |
| job | 작업 | 시간이 걸리는 검색·수집 한 건 |
| cache/API | 저장된 자료/새로 가져온 자료 | 인터넷을 썼는지 쉽게 알려주는 말 |

특히 `관심 유저`와 `메모`는 뜻을 나누는 것이 좋아요.

- 관심 유저는 “계속 살펴볼 사람”이에요.
- 메모는 그 사람에게 붙이는 설명이에요.
- 현재는 메모 내용을 지우면 관심 유저 행 자체가 사라질 수 있어요.
- 화면에서 단순히 `메모 삭제`라고만 보이면 DB 기본 조회 대상과 자동 수집 대상에서도 빠진다는 사실을
  사용자가 놓칠 수 있어요.

## 4. 현재 실제로 API가 호출되는 흐름

아래 표는 화면 이름이 아니라 **현재 코드가 실제로 하는 일**을 기준으로 정리했어요.

| 사용자 행동 | 현재 실제 흐름 | 외부 네트워크를 쓰나요? | 저장 내용을 바꾸나요? |
| --- | --- | --- | --- |
| 앱 화면을 열어요 | `/api/meta/options`를 요청하고, 그 안에서 게임 정보 확인과 앱 시작 자동 수집 조건 확인을 함께 해요. | 예. Data Dragon 버전 확인과 조건에 따른 경기 수집이 생길 수 있어요. | 게임 정보 캐시를 갱신할 수 있고, 자동 수집이 시작되면 경기 DB에도 써요. |
| 한 명을 검색해요 | Riot ID 확인 → 랭크 확인 → Match ID 목록 확인 → 캐시에 없는 경기 상세 확인 순서예요. | 예 | 원본 경기와 검색 인덱스를 저장할 수 있어요. |
| 여러 명을 수집해요 | 각 Riot ID 확인 → 사람별 Match ID 목록 확인 → 겹치는 경기 합치기 → 없는 상세 저장 → 인덱싱 순서예요. | 예 | 예 |
| 관심 유저 전체를 수집해요 | 여러 명 수집 칸에 관심 유저 Riot ID들을 넣어 같은 기능을 사용해요. | 예 | 예 |
| 앱 시작 시 자동 수집해요 | 별도 수집기가 아니라 여러 명 수집 기능을 다시 사용해요. | 예 | 예 |
| 저장된 매치업을 조회해요 | `matchup_index`에서 조건에 맞는 경기를 찾아요. 다만 직접 입력한 Riot ID의 계정 캐시가 오래됐으면 Account API를 호출할 수 있어요. | **경우에 따라 예** | 매치 인덱스는 읽기만 하지만, 외부에서 Riot ID를 확인하면 계정 캐시를 저장해요. |
| 경기 상세를 열어요 | 저장된 원본 경기를 사용하지만, 타임라인이 없거나 유효한 참가자 랭크 캐시가 없으면 관련 API를 호출해요. | **경우에 따라 많이 호출할 수 있어요.** | 새 타임라인과 랭크 캐시를 저장해요. |
| 게임 정보 갱신을 눌러요 | 챔피언·룬·주문 정적 데이터를 다시 확인해요. | Riot 경기 API가 아니라 Data Dragon을 사용해요. | 정적 데이터 캐시를 바꿔요. |

### 꼭 오해하지 말아야 할 점

- `저장된 매치업 조회`라는 이름만 보고 항상 인터넷을 전혀 쓰지 않는다고 생각하면 안 돼요.
  현재는 직접 입력한 Riot ID를 로컬에서 못 찾으면 Account API를 사용할 수 있어요.
- 경기 카드가 화면에 이미 있다고 해서 상세 열기가 항상 로컬 작업인 것은 아니에요.
  유효한 타임라인 또는 참가자 랭크 캐시가 없으면 추가 Riot API 호출이 생길 수 있어요.
- 앱 시작 시 자동 수집은 FastAPI 서버가 켜지는 즉시 시작되는 것이 아니에요.
  프런트가 처음 `/api/meta/options`를 요청할 때 검사하고 시작해요.
- 저장된 경기가 하나도 없는 첫 실행에서는 현재 자동 수집을 건너뛰어요.
  따라서 이름과 달리 “최초 실행 자동 수집”은 보장되지 않아요.
- `관심 유저 전체 수집`과 `앱 시작 시 자동 수집 대상`은 같은 목록이 아니에요.
  자동 수집은 관심 유저 중 자동 수집 스위치를 켠 사람만 대상으로 해요.
- DB 조회에서 Riot ID 입력칸을 비우면 DB에 등록된 모든 유저가 아니라 관심 유저 전체가 대상이에요.

## 5. 새로고침하면 어디까지 이어지나요?

이 부분은 현재 사용자 피드백이 가장 부족한 곳이에요.

| 상황 | 백엔드 작업 | 화면 상태 | 현재 결과 |
| --- | --- | --- | --- |
| 메뉴 탭만 바꿔요 | 계속돼요. | 숨겨진 화면이 그대로 살아 있어요. | 진행률과 입력이 유지돼요. 이 동작은 좋아요. |
| 개별 검색 중 브라우저 F5를 눌러요 | 같은 서버라면 뒤에서 계속될 수 있어요. | 화면이 `jobId`를 잃어요. | 진행 중 작업과 결과를 다시 찾지 못해요. |
| 수동 여러 명 수집 중 F5를 눌러요 | 같은 서버라면 뒤에서 계속될 수 있어요. | 화면이 `jobId`를 잃어요. | 진행 중 작업과 결과를 다시 찾지 못해요. |
| 앱 시작 자동 수집 중 F5를 눌러요 | 같은 서버라면 계속돼요. | meta에서 자동 수집 `jobId`를 다시 받아요. | 자동 수집만 진행 표시를 다시 이어갈 수 있어요. |
| DB 조회 뒤 F5를 눌러요 | 긴 작업이 아니므로 해당 없어요. | 입력 조건, 페이지, 결과가 사라져요. | 기본 DB 화면으로 돌아가요. |
| 백엔드 서버가 다시 시작돼요 | 기존 작업 스레드와 작업 기록이 사라져요. | 예전 `jobId`로 결과를 찾을 수 없어요. | 작업을 정확한 중단 지점부터 이어갈 수 없어요. |
| 상태 확인 중 잠깐 통신 오류가 나요 | 서버에서는 작업이 계속될 수 있어요. | 현재 polling은 멈춰요. | 사용자는 작업도 멈춘 것으로 오해할 수 있어요. |

### “이어진다”는 말도 두 가지로 나눠야 해요

1. **작업 화면 다시 연결**
   - 같은 서버에서 계속 돌고 있는 작업을 F5 뒤 다시 찾아 진행률과 결과를 보여주는 일이에요.
2. **서버 재시작 뒤 정확히 재개**
   - 서버가 꺼졌다 켜져도 마지막 처리 지점부터 다시 이어가는 일이에요.

일반 개별 검색·수동 여러 명 수집의 F5 재연결과 서버 재시작 뒤 정확한 재개는 보장되지 않아요.
같은 서버에서 실행 중인 앱 시작 자동 수집만 F5 뒤 다시 연결되는 예외가 있어요.
SQLite에 이미 저장된 경기 일부는 남기 때문에 다음 실행에서 캐시를 재사용할 수는 있어요.
하지만 이것은 **중간부터 정확히 이어서 하는 것**이 아니라 **처음 목록부터 다시 확인하되 이미 저장된 것은 재사용하는 것**이에요.

### 바라는 상태

- 모든 긴 작업은 종류와 관계없이 다시 찾을 수 있어야 해요.
- 작업에는 대상, 시작 시각, 현재 단계, 성공·실패 수, 마지막 처리 위치, 종료 이유가 보여야 해요.
- F5 뒤에는 진행 중 작업으로 다시 연결해야 해요.
- 잠깐 연결이 끊기면 `서버에서 작업은 계속되고 있어요. 다시 연결하는 중이에요.`라고 알려줘야 해요.
- 서버가 다시 시작되어 기록을 찾을 수 없으면 `완료`, `실패`와 다른 `중단됨` 상태로 알려줘야 해요.
- 이미 저장한 데이터와 아직 저장하지 못한 범위를 구분해 보여줘야 해요.

어떤 저장 방법을 쓸지는 구현자가 정하면 돼요. 중요한 것은 사용자가 새로고침을 두려워하지 않고,
화면에 나온 상태를 믿을 수 있어야 한다는 점이에요.

## 6. 주요 문제와 바라는 상태

### 6-1. 자동 수집이 사람별 최신 상태를 보지 않아요

#### 현재 문제

자동 수집 대상마다 `last_collected_at` 필드와 기록을 조회할 수 있는데도,
실제 수집 기간은 DB 전체에서 가장 최근인 경기 한 건을 기준으로 정해요.
이 값은 한 번도 수집하지 않은 대상에게는 비어 있을 수 있어요.
사이드바에 표시하는 마지막 수집 시각도 값이 있는 대상 중 가장 최근 값 하나만 사용해요.

쉽게 말하면 15명의 숙제를 검사하면서 가장 최근에 숙제한 한 명만 보고
“모두 숙제를 했네”라고 판단하는 것과 비슷해요.

#### 왜 문제가 되나요?

- 개별 검색으로 전혀 다른 사람의 오늘 경기가 저장되면, 오래된 관심 유저도 최신이라고 잘못 판단할 수 있어요.
- 어제 확인했지만 최근에 게임을 하지 않은 사람은 경기 날짜가 오래됐다는 이유로 다시 긴 수집을 할 수 있어요.
- 한 번도 수집하지 않은 사람이 있어도 다른 한 명의 최신 시각에 가려질 수 있어요.
- 첫 DB가 비어 있으면 자동 수집을 건너뛰기 때문에 첫 사용자 흐름과 맞지 않아요.

#### 바라는 상태

- 최신 여부는 관심 유저 한 명씩 따로 판단해야 해요.
- 각 사람에게 `한 번도 수집하지 않음`, `최신`, `수집 필요`, `부분 완료`, `실패`가 보여야 해요.
- 새로 등록한 사람과 오랫동안 수집하지 않은 사람의 범위를 다르게 판단할 수 있어야 해요.
- 일부만 오래됐다면 그 사람들만 수집해야 해요.
- 전체 요약은 `15명 중 최신 12명 · 수집 필요 2명 · 미수집 1명`처럼 보여주는 편이 정확해요.

---

### 6-2. `수집 성공`이 실제 저장 완료보다 먼저 기록돼요

#### 현재 문제

여러 명 수집은 한 사람의 Match ID 목록을 받자마자 성공 수를 올리고 마지막 수집 시각을 기록해요.
실제 경기 상세 다운로드와 검색 인덱스 저장은 그 뒤에 이루어져요.

#### 왜 문제가 되나요?

- 뒤 단계에서 오류가 나거나 서버가 꺼져도 그 사람은 성공한 것처럼 남을 수 있어요.
- `1명 성공`이 “목록을 받음”인지 “모든 상세를 저장함”인지 알 수 없어요.
- 정해진 최대 경기 수에서 목록이 잘려도 더 남았는지 표시되지 않아요.
- 화면의 마지막 수집 시각과 관심 유저 상태가 실제 저장 완료보다 앞서 보일 수 있어요.
- 나중에 사람별 이어받기 기준을 만들 때 이 이른 기록을 그대로 믿으면 잘못 건너뛸 위험이 있어요.
- Riot ID 확인 실패는 사람별로 나누지만, 그 뒤 Match ID 목록 확인 오류는 전체 작업을 멈출 수 있어요.
- 겹친 Match ID를 집합으로 합친 뒤 순서가 사라져, 중간에 멈추면 어느 경기부터 저장됐는지 일정하지 않을 수 있어요.

#### 바라는 상태

- `Riot ID 확인 → 경기 목록 확인 → 경기 상세 저장 → 조회용 인덱스 완료` 단계를 구분해야 해요.
- 마지막 성공 시각은 그 사람에게 필요한 저장 단계가 끝난 뒤에만 기록해야 해요.
- 일부만 끝났으면 성공이 아니라 `부분 완료`라고 보여줘야 해요.
- 실패한 사람마다 어느 단계에서 멈췄는지 알려줘야 해요.
- 최대 개수 때문에 더 남았으면 `여기까지 받았고 더 남아 있음`을 알 수 있어야 해요.
- 한 사람의 오류가 다른 사람의 저장 완료 상태까지 지우지 않아야 해요.

---

### 6-3. 모든 수집 작업을 한곳에서 조정하지 않아요

#### 현재 문제

개별 검색, 수동 여러 명 수집, 앱 시작 자동 수집이 각각 별도 작업을 만들어요.
같은 버튼을 빠르게 두 번 눌러도 새 작업이 두 개 생길 수 있고,
자동 수집 중에 같은 사람들을 수동으로 다시 수집할 수도 있어요.

같은 작업 안에서는 여러 사람에게 겹치는 Match ID를 한 번으로 합치는 좋은 처리가 있어요.
하지만 서로 다른 작업끼리는 진행 중인 요청을 공유하지 않아요.
공통 중복 방지 장치가 없다는 점은 코드로 확인했지만,
실제 Riot API 중복 호출량은 라이브 수집을 실행하지 않았으므로 측정하지 않았어요.

#### 왜 문제가 되나요?

- 같은 사람의 Match ID 목록을 여러 번 받을 수 있어요.
- 두 작업이 동시에 같은 경기의 캐시를 확인하면 둘 다 “없음”이라고 보고 같은 상세 API를 호출할 수 있어요.
- Riot API 제한을 각 스레드가 따로 만나므로 전체 대기 상태를 알기 어려워요.
- SQLite 쓰기가 겹치면 느려지거나 잠금 충돌이 날 가능성이 있어요.
  다만 실제 잠금 오류가 발생했다는 증거는 아직 없으므로, 이것은 구조상 위험으로만 봐야 해요.
- 화면은 마지막으로 받은 `jobId` 하나만 추적해 앞선 작업이 보이지 않게 될 수 있어요.

#### 바라는 상태

- 한 명, 여러 명, 자동 수집이 같은 수집 조정 흐름을 사용해야 해요.
- 같은 대상과 기간의 작업이 이미 진행 중이면 새 작업을 만들지 말고 기존 작업을 보여줘야 해요.
- 같은 Match ID를 가져오는 중이면 그 결과를 함께 기다려야 해요.
- Riot API 호출 제한과 대기 시간을 모든 수집 작업이 공유해야 해요.
- 버튼은 누르는 순간 `작업을 만드는 중`으로 바뀌고, 같은 요청을 연속으로 누를 수 없어야 해요.
- 다른 화면에서도 `현재 15명 수집 중` 같은 공용 배지를 볼 수 있어야 해요.

---

### 6-4. 이미 PUUID를 아는데 Riot ID로 되돌렸다가 다시 찾고 있어요

#### 현재 문제

앱 시작 자동 수집 대상에는 이미 PUUID가 저장돼 있어요.
그런데 현재는 PUUID를 바로 쓰지 않고 Riot ID 문자열로 되돌린 다음,
여러 명 수집 안에서 Riot ID를 다시 PUUID로 바꿔요.

#### 왜 문제가 되나요?

- 계정 캐시가 7일을 넘으면 이미 아는 사람도 Account API를 다시 호출할 수 있어요.
- 그동안 닉네임이 바뀌었다면 옛 Riot ID 조회가 실패할 수 있어요.
- 변하지 않는 식별자인 PUUID를 가지고도 표시 이름 때문에 수집 전체가 실패할 수 있어요.
- Riot ID 해석 코드가 개별 검색, 여러 명 수집, DB 조회, 메모 등록에 따로 있어
  화면마다 캐시와 로컬 등록부를 사용하는 규칙이 달라요.

#### 바라는 상태

- 이미 PUUID를 아는 자동 대상은 그 PUUID로 바로 수집해야 해요.
- 사용자가 새 Riot ID를 직접 입력했을 때만 Riot ID 확인이 필요해요.
- Riot ID를 로컬에서 찾는 순서와 외부 API를 사용할 조건을 모든 화면이 공유해야 해요.
- 닉네임 갱신과 경기 수집 성공을 서로 다른 문제로 다뤄야 해요.

2026-08-31 읽기 전용 DB 집계에서는 자동 수집 대상 15명 모두에게 계정 캐시 행이 있었지만,
15명 모두 7일 유효기간이 지난 상태였어요. 현재 구조로 자동 수집하면 이미 PUUID를 아는데도
대상 수만큼 Account API 확인이 생길 수 있는 사례였어요.
이 숫자는 시간이 지나면 달라질 수 있는 참고값이에요.

---

### 6-5. `저장된 매치업 조회`가 완전히 로컬 전용이 아니에요

#### 현재 문제

DB 검색 서비스는 “Riot API 호출 없이 조회한다”고 설명하지만,
그 앞에서 사용자가 입력한 Riot ID를 PUUID로 바꾸는 과정은 Account API를 호출할 수 있어요.
로컬 `player_registry`에 이미 아는 사람이 있어도 DB 조회 경로는 그 등록부를 먼저 사용하지 않아요.

#### 왜 문제가 되나요?

- 인터넷 없이 저장된 경기만 보고 싶어도 API 키나 네트워크 문제 때문에 조회가 실패할 수 있어요.
- 사용자는 `DB 조회`라는 이름을 보고 외부 호출이 없다고 믿기 쉬워요.
- 같은 사람을 메모 등록할 때는 로컬 등록부에서 찾고, DB 조회할 때는 다시 API를 부를 수 있어
  규칙이 일관되지 않아요.

#### 바라는 상태

- 저장된 매치업 조회는 먼저 로컬 정보만 사용해야 해요.
- 로컬에서 모르는 Riot ID라면 몰래 외부 호출하지 말고
  `저장된 유저가 아니어서 Riot에서 한 번 확인해야 해요.`라고 실행 전에 알려줘야 해요.
- 더 단순하게는 DB 조회에서는 `로컬에서 찾지 못함`을 보여주고,
  온라인 확인은 `새 데이터 가져오기` 흐름으로 안내해도 좋아요.
- 어떤 선택을 하든 화면 문구와 실제 호출이 반드시 같아야 해요.

---

### 6-6. 작업 상태가 화면마다 따로 있고 새로고침 복구도 달라요

#### 현재 문제

개별 검색과 여러 명 수집의 `jobId`는 각 React 화면 메모리에만 있어요.
자동 수집만 meta가 `jobId`를 다시 알려줘요. 백엔드 작업 기록도 서버 메모리에만 있어요.
자동 수집도 내부 발견 경로에는 수동 여러 명 수집과 같은 `manual_multi`로 기록돼
나중에 어떤 방식으로 시작된 수집인지 구분하기 어려워요.

#### 왜 문제가 되나요?

- F5 뒤에 백엔드는 계속 일하지만 화면은 작업을 잃어버려요.
- 완료 결과를 다시 열 방법이 없어요.
- 다른 메뉴에서는 어떤 작업이 진행 중인지 알 수 없어요.
- 상태 확인 GET이 한 번 실패하면 polling이 멈추고, 사용자는 실제 서버 작업 상태를 몰라요.
- 서버 재시작, 일시적인 연결 끊김, 실제 작업 실패가 비슷한 오류처럼 보일 수 있어요.
- 완료된 작업을 정리하는 기준과 최근 작업 목록이 없어 서버가 살아 있는 동안 기록이 계속 쌓여요.
- 성공하면 진행 상자는 바로 사라져요. 현재 탭의 결과 요약은 남지만, 진행 세부 내용은 사라지고
  F5 뒤에는 완료 결과나 최근 작업 이력도 다시 찾지 못해요.

#### 바라는 상태

- 모든 작업을 보여주는 공용 `경기 데이터 현황`이 필요해요.
- F5 뒤에 최근 진행 중 작업과 완료 결과를 다시 찾을 수 있어야 해요.
- 서버 작업은 계속되지만 화면 연결만 끊긴 경우에는 자동으로 다시 연결해야 해요.
- 서버 재시작으로 작업 기록을 찾지 못하는 경우는 `중단됨`으로 명확히 구분해야 해요.
- 완료 카드는 즉시 사라지지 않고 사용자가 확인할 때까지 남는 것이 좋아요.
- 자동인지 수동인지, 누가 어떤 화면에서 시작했는지도 작업 기록에서 구분되어야 해요.

---

### 6-7. 메모 목록을 여러 번 가져오면서도 서로 최신 상태가 아니에요

#### 현재 문제

검색, 여러 명 수집, DB 조회 화면은 탭 상태를 지키기 위해 모두 동시에 마운트돼 있어요.
그런데 세 화면이 각각 `/api/player-memos`를 요청하고 자기만의 목록을 가지고 있어요.

#### 왜 문제가 되나요?

- 앱을 처음 열 때 같은 메모 목록을 최소 3번 요청해요.
- Vite 개발 실행과 React Strict Mode에서는 effect 확인이 겹쳐 더 많이 호출될 수 있어요.
- 메모 관리에서 사람을 추가·수정·삭제해도 다른 화면의 선택 목록은 F5 전까지 예전 상태일 수 있어요.
- 메모 불러오기가 실패해도 빈 목록으로 바뀌어 `관심 유저 0명`처럼 보여요.

#### 바라는 상태

- 관심 유저 목록은 앱에서 한 번 불러와 모든 화면이 같이 사용해야 해요.
- 추가·수정·삭제 뒤 같은 공용 목록만 갱신하면 모든 화면이 즉시 바뀌어야 해요.
- `불러오는 중`, `0명`, `불러오기 실패`, `정상` 상태를 서로 다르게 보여줘야 해요.
- 탭을 바꿔도 입력과 작업 상태가 유지되는 현재 장점은 그대로 두는 것이 좋아요.

---

### 6-8. 화면의 API·캐시·성공 숫자가 실제 뜻과 달라요

#### 현재 문제

- 개별 검색의 `api_calls`에는 Account API와 Match ID 목록 호출이 포함되지 않아요.
- 여러 명 수집은 Match ID 목록이 여러 페이지여도 사람당 1회로만 더해요.
- 429 재시도와 상세 패널에서 생긴 호출도 기존 요약 숫자에 포함되지 않아요.
- `indexed_rows`는 새로 생긴 행뿐 아니라 기존 행을 다시 처리한 수도 포함해요.
- 여러 명 수집의 `success_count`는 상세 저장 완료가 아니라 Match ID 목록 확인 성공에 가까워요.

#### 왜 문제가 되나요?

사용자는 `API 30`을 실제 인터넷 요청 30번으로,
`인덱스 500행`을 새 데이터 500개로,
`15명 성공`을 모든 데이터 저장 완료로 이해하기 쉬워요.
하지만 현재 숫자는 그 뜻을 보장하지 않아요.

#### 바라는 상태

- 실제 외부 HTTP 요청을 보내는 한곳에서 endpoint별 호출과 재시도를 세어야 해요.
- 기본 화면에는 `저장된 자료에서 찾음`, `인터넷에서 새로 가져옴`, `새 경기 저장`,
  `기존 경기 다시 확인`처럼 쉬운 말로 보여줘야 해요.
- 기술적인 endpoint별 숫자는 `자세히 보기`에 두는 것이 좋아요.
- `성공`, `부분 완료`, `실패`, `중단`의 뜻을 정확히 나눠야 해요.

---

### 6-9. 수집이 끝나도 다른 화면의 숫자가 그대로예요

#### 현재 문제

개별 검색과 수동 여러 명 수집이 끝나면 해당 결과만 저장해요.
사이드바 meta를 다시 읽지 않기 때문에 실제 DB 경기 수와 마지막 경기 날짜가 늘어도 예전 숫자가 남아요.
관심 유저별 경기 수와 이미 열어 둔 DB 결과도 새 데이터가 들어온 사실을 몰라요.

자동 수집 완료 때만 meta를 다시 읽어 이 동작도 서로 달라요.

#### 왜 문제가 되나요?

- 성공 메시지는 떴는데 DB 숫자가 그대로라 실패한 것처럼 보여요.
- 반대로 오래된 DB 결과를 최신 결과라고 믿을 수 있어요.
- 화면마다 갱신 규칙이 달라 앱을 믿기 어려워요.

#### 바라는 상태

- 어떤 수집이든 끝나면 DB 현황과 관심 유저 상태를 함께 최신으로 바꿔야 해요.
- 이미 DB 결과가 열려 있다면 `새 데이터가 들어왔어요. 다시 조회할까요?`라고 알려줘야 해요.
- 게임 정보 갱신은 경기 수집 완료 후 상태 갱신과 다른 일이므로 따로 다뤄야 해요.

---

### 6-10. 캐시된 경기에도 무거운 DB 작업을 반복해요

#### 현재 문제

개별 검색과 여러 명 수집은 캐시에 이미 있던 경기에도 `index_match()`를 다시 실행해요.
한 경기를 인덱싱할 때 유효한 참가자 최대 10명의 행을 다시 넣고,
관련 선수들의 챔피언 통계를 전체 기록에서 다시 계산해요.

쉽게 말하면 카드 한 장을 다시 확인할 때마다 관련된 열 명의 공책을 처음부터 다시 세는 것과 비슷해요.

#### 왜 문제가 되나요?

- 저장된 경기가 많아질수록 “새 경기 확인”보다 “이미 한 일을 다시 계산”하는 시간이 커질 수 있어요.
- 동시에 여러 수집이 실행되면 같은 재계산이 겹칠 수 있어요.
- 화면의 인덱스 숫자는 새로 추가된 양처럼 보이지만 실제로는 반복 처리도 포함해요.

#### 바라는 상태

- 새 경기, 조회용 인덱스가 빠진 경기, 명시적으로 인덱스 버전 갱신이 필요한 경기만
  다시 처리하는 것이 좋아요.
- 한 작업에서 바뀐 사람들을 모아 통계는 필요한 만큼만 다시 계산해야 해요.
- `새로 추가`, `기존 갱신`, `변경 없음`을 구분할 수 있어야 해요.

---

### 6-11. DB 조회 페이지와 CSV가 화면과 다른 조건을 쓸 수 있어요

#### 현재 문제

DB 결과를 본 뒤 입력 조건만 바꿔도 예전 결과는 화면에 그대로 남아요.
그 상태에서 페이지를 바꾸거나 CSV를 누르면 마지막으로 실행한 조건이 아니라
현재 편집 중인 새 조건으로 서버를 다시 호출할 수 있어요.

또한 DB 검색은 페이지 한 장만 필요해도 일치하는 결과 전체를 읽은 뒤 Python에서 잘라요.
CSV도 화면 결과를 재사용하지 않고 검색을 다시 실행해요.

#### 왜 문제가 되나요?

- 화면에 보이는 결과와 내려받은 CSV 내용이 달라질 수 있어요.
- 늦게 끝난 예전 요청이 더 최근 결과를 덮어쓸 수 있어요.
- 데이터가 커질수록 한 페이지를 보기 위해 불필요하게 많은 행을 읽게 돼요.

#### 바라는 상태

- `편집 중 조건`과 `마지막으로 적용한 조건`을 분리해야 해요.
- 페이지 이동, 결과 제목, CSV는 마지막 적용 조건만 사용해야 해요.
- 조건을 바꾸면 `아직 적용되지 않은 변경이 있어요.`라고 보여줘야 해요.
- 화면과 CSV는 같은 조건과 같은 기준 시점을 사용해야 해요.
- 페이지는 필요한 범위만 DB에서 읽는 것이 좋아요.
- 여러 조회가 겹쳐도 가장 최근 요청의 결과만 화면에 반영되어야 해요.

---

### 6-12. 경기 상세 하나가 필요 없는 정보까지 함께 가져와요

#### 현재 문제

경기 상세 패널을 열면 저장된 경기 정보 외에 타임라인과 최대 10명의 랭크 정보까지 한 번에 붙여요.
기본 탭이 빌드여도 종합 탭용 랭크를 기다릴 수 있고,
종합만 보려 해도 빌드용 타임라인을 확인할 수 있어요.

#### 왜 문제가 되나요?

- 상세 하나가 예상보다 느리고 Riot API를 많이 쓸 수 있어요.
- API 키 오류나 429처럼 모두에게 공통인 문제가 생겨도 참가자마다 비슷한 호출을 계속 시도할 수 있어요.
- 패널을 닫았다 다시 열면 상세 endpoint를 다시 호출해요.
- 개별 검색에서는 랭크가 없는 사람의 캐시를 다시 쓰지 않아 외부 조회를 반복할 수 있어요.

#### 바라는 상태

- 저장된 기본 경기 정보는 즉시 보여줘야 해요.
- 빌드에 필요한 타임라인은 빌드 탭에서, 참가자 랭크는 종합 탭에서 필요할 때 확인하는 것이 좋아요.
- 같은 경기와 참가자의 완료된 결과와 진행 중 요청을 여러 화면이 공유해야 해요.
- 개별 검색의 랭크 확인에서도 `랭크 없음`을 정상적인 캐시 결과로 재사용해야 해요.
- 상세 열기 전에 `저장된 정보가 없으면 타임라인과 랭크를 새로 확인해요.`라고 알려줘야 해요.

---

### 6-13. 최초 화면의 읽기 요청 안에 실제 수집 시작이 숨어 있어요

#### 현재 문제

이름만 보면 `/api/meta/options`는 화면에 필요한 정보를 읽는 API예요.
하지만 이 요청 안에서 게임 정보 최신 확인과 앱 시작 자동 수집 시작까지 할 수 있어요.
최초 화면에는 그동안 `메타데이터를 불러오는 중...`만 보여요.

챔피언 저장소와 룬·주문 저장소는 같은 Data Dragon 버전 URL을 각각 확인해
한 번의 초기 확인에도 중복 네트워크 작업이 생겨요.

#### 왜 문제가 되나요?

- 단순 조회처럼 보이는 호출이 데이터를 쓰는 긴 작업을 시작해 흐름을 추적하기 어려워요.
- 프런트 초기 요청이 두 번 들어오면 게임 정보 확인도 겹칠 가능성이 있어요.
- 사용자는 프로그램이 멈춘 것인지, 게임 정보를 받는지, 관심 유저 경기를 수집하는지 몰라요.

#### 바라는 상태

- 앱 시작 시 한 번 해야 하는 검사와 화면 meta 조회의 역할을 분명히 나누는 것이 좋아요.
- 같은 초기 요청이 여러 번 들어와도 실제 확인과 수집은 한 번만 이루어져야 해요.
- Data Dragon 버전은 한 번 확인해 챔피언·룬·주문 갱신이 같은 결과를 공유해야 해요.
- 최초 화면에는 아래처럼 쉬운 단계를 보여줘야 해요.

```text
1. 게임 정보 확인 중
2. 관심 유저 상태 확인 중
3. 자동 수집 시작 / 최신이라 건너뜀 / 첫 수집 필요
```

## 7. 중복 호출과 반복 작업만 따로 모아 본 표

| 중복 또는 반복 | 현재 확인된 이유 | 사용자에게 생기는 일 | 바라는 상태 |
| --- | --- | --- | --- |
| `/api/player-memos` 최소 3회 | 숨겨진 세 작업 화면이 각자 목록을 가져와요. | 첫 화면 호출이 늘고 목록끼리 달라질 수 있어요. | 공용 관심 유저 목록 한 개를 같이 사용해요. |
| Data Dragon 버전 확인 2회 이상 가능 | 챔피언과 룬·주문 저장소가 같은 버전 URL을 따로 확인해요. | 시작이 느려지고 이유 없는 외부 호출이 생겨요. | 버전 확인 결과를 한 번만 받아 공유해요. |
| 자동 대상 Account API 재확인 | 이미 가진 PUUID를 Riot ID로 되돌려요. | 이름 변경이나 캐시 만료로 불필요한 실패가 생겨요. | 알려진 PUUID를 바로 사용해요. |
| 경기 캐시 DB 확인 2회 | 호출하는 쪽과 상세 가져오기 함수가 각각 캐시를 확인해요. | 경기마다 작은 DB 작업이 반복돼요. | 한 번 확인한 결과를 같은 흐름에서 재사용해요. |
| 같은 경기 상세 API 중복 가능 | 서로 다른 job 사이에 진행 중 요청 공유가 없어요. | API 제한을 더 빨리 쓰고 같은 데이터를 두 번 받아요. | 같은 Match ID 작업을 공유해요. |
| 캐시된 경기 인덱싱 반복 | 검색·수집 때 기존 경기에도 인덱싱을 다시 해요. | DB가 커질수록 다시 계산하는 시간이 늘어요. | 새 경기와 누락된 인덱스만 처리해요. |
| DB 전체 결과 재조회 | 페이지와 CSV가 검색 전체를 다시 실행해요. | 화면과 파일 조건이 달라지고 큰 DB에서 느려져요. | 적용 조건을 고정하고 필요한 범위만 읽어요. |
| 상세의 타임라인·10명 랭크 묶음 | 상세 endpoint가 모든 보조 정보를 한 번에 붙여요. | 상세 하나가 많은 외부 호출을 만들 수 있어요. | 탭에서 필요한 정보만 늦게 가져와요. |

`/api/jobs/{id}` 상태를 일정 간격으로 다시 묻는 것은 진행률을 보여주기 위한 정상적인 polling이에요.
이 호출 자체를 중복으로 없애는 것이 목표는 아니에요. 일시적인 실패 뒤 재연결, 작업 완료 뒤 중단,
화면 전체에서 같은 작업 상태 공유가 제대로 되어야 해요.

Match ID 목록도 여러 페이지를 가져오려면 여러 요청이 필요한 것이 정상이에요.
문제는 필요한 페이지 호출까지 한 번으로 잘못 세어 실제 API 사용량을 숨기는 점이에요.

## 8. 데이터 이름과 실제 숫자도 맞춰야 해요

### 8-1. 사이드바 `DB 매치` 숫자는 조회 가능한 경기 수와 달라요

현재 사이드바의 DB 경기 수는 원본 `match_cache` 개수예요.
실제 저장된 매치업 조회는 `matchup_index`를 사용해요.

2026-08-31 읽기 전용 집계에서는 다음처럼 차이가 있었어요.

- 원본 경기 캐시: 5,967경기
- 조회 인덱스: 4,133경기, 41,320행
- 앱 시작 자동 수집 대상: 15명

이 숫자는 계속 달라질 수 있어요. 중요한 점은 **원본을 가진 경기 수와 검색 가능한 경기 수가 같은 뜻이
아니라는 것**이에요.

#### 바라는 상태

- `보관한 원본 경기`와 `매치업 조회 가능 경기`를 구분해 보여줘야 해요.
- 사용자가 왜 두 숫자가 다른지 짧게 설명해야 해요.
- 자동 수집의 최신 판단에 어떤 숫자와 날짜를 사용하는지도 분명해야 해요.

### 8-2. 들어온 길에 따라 인덱스 저장 기준이 달라요

개별 검색은 대상의 랭크가 다이아 이상일 때만 경기 인덱싱을 허용해요.
여러 명 수집은 같은 티어 확인 없이 모든 경기를 인덱싱해요.

그래서 같은 유저라도 개별 검색으로 봤을 때는 DB 조회에 안 나오고,
여러 명 수집 뒤에는 DB 조회에 나올 수 있어요.

#### 바라는 상태

- 고티어 경기만 모으는 도구인지, 관심 유저 경기는 모두 모으는 도구인지 원칙을 하나로 정해야 해요.
- 어느 원칙을 택하든 `화면에서 확인함`, `원본 저장됨`, `매치업 조회 가능`을 구분해 보여줘야 해요.
- 이 선택은 제품 의미에 영향을 주므로 구현자가 조용히 추측해서 바꾸면 안 돼요.

## 9. 권장 화면 흐름

화면을 완전히 새로 디자인할 필요는 없어요.
현재 카드와 반응형 레이아웃을 유지하면서 메뉴의 의미와 상태 피드백을 아래처럼 정리하는 것이 좋아요.

### 9-1. 저장된 매치업 보기

현재 기본 DB 조회 화면을 유지해도 좋아요.

화면 위에 먼저 보여줄 내용은 다음과 같아요.

- 현재 조회 대상: `관심 유저 15명` 또는 `직접 선택한 3명`
- 사용 데이터: `내 컴퓨터에 저장된 경기`
- 마지막 데이터 수집 시각과 수집이 필요한 인원
- 마지막으로 적용한 검색 조건
- 결과 경기 수와 중복을 뺀 상대 Riot ID 수

`전체 관심 유저` 선택은 긴 Riot ID 문자열을 입력칸에 넣는 방식보다
대상 범위 자체를 고르는 선택으로 보여주는 것이 쉬워요.

빈 결과도 이유에 따라 달라야 해요.

- 관심 유저가 없어요.
- 저장된 경기가 없어요.
- 이 조건에 맞는 경기가 없어요.
- 직접 입력한 Riot ID를 로컬에서 찾지 못했어요.
- 조건이 바뀌었지만 아직 다시 조회하지 않았어요.

### 9-2. 새 데이터 가져오기

현재 `개별 유저 검색`과 `유저 매치 수집`은 사용 목적이 다르지만,
Riot에서 경기 데이터를 확인하고 저장하는 내부 흐름은 많이 겹쳐요.

두 화면을 반드시 하나로 합칠 필요는 없어요.
한 명을 바로 찾는 원래 기능은 눈에 잘 띄는 지름길로 유지하고,
두 화면이 `새 데이터 가져오기`라는 같은 기능군과 공용 작업 상태를 사용한다는 관계만 분명히 보여줘도 돼요.
한 화면으로 묶는다면 안에서 목적을 바로 고를 수 있어야 해요.

- 한 명 빠르게 확인
- 선택한 관심 유저 수집
- 관심 유저 전체 수집
- 앱 시작 자동 수집 설정

실행 전에는 최소한 아래 내용을 알려줘야 해요.

- 대상이 몇 명인지
- 어느 기간을 확인하는지
- 사람당 최대 몇 경기를 확인하는지
- 저장된 자료만 쓰는지 Riot API를 호출하는지
- 같은 범위의 작업이 이미 진행 중인지

### 9-3. 공용 경기 데이터 현황

작은 사이드바 카드만으로 모든 상태를 설명하기는 어려워요.
화면 위쪽이나 쉽게 열 수 있는 곳에 공용 작업 현황을 두는 것이 좋아요.

다음 정보가 있으면 충분해요.

- 작업 이름: 자동 수집 / 직접 시작한 수집 / 한 명 검색
- 대상: 15명 중 현재 7번째
- 단계: Riot ID 확인 / 경기 목록 / 상세 저장 / 인덱스
- 이번 결과: 새 경기, 기존 경기, 실패 인원
- Riot API 대기 또는 연결 재시도 여부
- 시작 시각, 마지막 진행 시각, 완료 시각
- `이어서 보기`, `다시 연결`, `실패한 사람만 보기`

완료되면 진행 상자를 바로 없애지 말고 아래처럼 남기는 편이 좋아요.

```text
수집 완료
15명 중 14명 완료 · 1명 실패
새 경기 24개 · 저장된 경기 재사용 180개
완료 시각 14:32
```

### 9-4. 관심 유저 관리

관심 유저 한 명마다 다음 상태를 함께 보여주는 것이 좋아요.

- Riot ID와 메모
- 앱 시작 자동 수집 사용 여부
- 마지막으로 확인한 시각
- 마지막으로 완전히 저장한 시각
- 최신 / 수집 필요 / 미수집 / 부분 완료 / 실패
- 마지막 실패 이유

메모나 유저를 삭제할 때는 단순 글 삭제인지 관심 유저 전체 삭제인지 분명히 물어야 해요.
관심 유저 전체 삭제라면 `DB 기본 조회와 자동 수집 대상에서도 빠져요.`라고 알려줘야 해요.

### 9-5. 결과에서 프로젝트 본질을 다시 눈에 띄게 해요

초기 목적이었던 상대 Riot ID 활용이 현재는 경기 카드 하나씩 복사하는 기능으로 약해졌어요.
결과 상단에 다음 행동을 두는 것이 좋아요.

- 상대 Riot ID 전체 복사
- 중복 제거 후 몇 명인지 표시
- 선택한 경기만 복사
- CSV 다운로드

풍부한 경기 카드는 그대로 유지하고, 자주 쓰는 전체 복사만 결과의 대표 행동으로 올리면 돼요.

## 10. 작지만 실제로 고칠 가치가 있는 UI 문제

### 10-1. `최근검색`이 실제 최근 순서가 아니에요

세 최근검색 목록의 순서 규칙이 서로 달라요.

- 상대 챔피언은 항상 가나다순으로 다시 정렬해 실제 최근 순서가 아니에요.
- Riot ID는 저장 개수에 따라 정렬되는 때와 입력 순서가 남는 때가 달라요.
- 기준 챔피언은 입력 순서를 유지해요.

정말 최근검색이라면 세 목록 모두 가장 최근에 사용한 순서로 보여줘야 해요.
가나다순을 유지하고 싶다면 해당 목록의 이름을 `저장된 목록`으로 바꾸는 것이 맞아요.

### 10-2. 한국 시간 오전에는 기본 날짜가 하루 전일 수 있어요

기본 날짜가 UTC 기준 `toISOString()`으로 만들어져요.
한국 시간 자정부터 오전 9시 사이에는 오늘이 전날로 들어갈 수 있어요.

- 사용자의 로컬 날짜를 기준으로 표시해야 해요.

### 10-3. 오류와 빈 상태가 서로 비슷해요

- 메모 불러오기 실패가 메모 0명처럼 보여요.
- 첫 meta 로딩 실패에 바로 보이는 재시도 행동이 부족해요.
- 작업 생성 POST, CSV 다운로드, 클립보드 복사 실패가 충분히 설명되지 않아요.
- DB 결과 0건도 원인과 관계없이 비슷한 안내를 보여줘요.

오류 문구에는 다음 세 가지가 있으면 좋아요.

1. 무엇이 실패했는지
2. 뒤의 서버 작업은 계속되는지
3. 사용자가 지금 무엇을 누르면 되는지

### 10-4. 기술 용어가 앞에 너무 많이 보여요

`DB`, `row`, `PUUID`, `Data Dragon`, `캐시/API`는 개발자에게는 익숙하지만 처음 쓰는 사람에게는 어려워요.

- 기본 화면은 `저장된 경기`, `관심 유저`, `새로 가져온 경기`처럼 쉬운 말을 써요.
- 기술 정보는 `자세히`에서 보여주는 것이 좋아요.

### 10-5. 진행 상태를 화면 읽기 도구도 알 수 있어야 해요

- 진행 문구가 바뀔 때 알릴 수 있는 상태 영역이 필요해요.
- 작업 중인 영역과 버튼은 실제 진행·비활성 상태를 알려야 해요.
- 색만으로 성공·실패·대기를 구분하지 않는 것이 좋아요.

## 11. 코드 구조는 기능 흐름을 정한 뒤 나누는 것이 좋아요

현재 주요 파일은 매우 커요.

- `frontend/src/App.tsx`: 약 3,388줄
- `src/api/main.py`: 약 1,386줄
- `src/cache.py`: 약 1,259줄
- `frontend/src/styles.css`: 약 2,402줄

하지만 큰 파일 하나에 있다는 것과 중앙에서 한 번 관리된다는 것은 다른 말이에요.
현재는 큰 파일 안에서도 메모 목록, 작업 상태, Riot ID 해석 규칙이 여러 복사본으로 나뉘어 있어요.

### 바라는 상태

- 프런트는 공용 meta, 관심 유저, 진행 중 작업 상태를 한 번만 관리해야 해요.
- 백엔드는 Riot ID 확인 규칙, 수집 조정, 작업 기록, 게임 정보 갱신의 책임이 서로 분명해야 해요.
- 파일을 나누는 일 자체보다 “같은 사실을 한곳에서 관리한다”는 결과가 더 중요해요.
- 동작을 먼저 바로잡고, 그 경계를 따라 파일을 나누는 것이 좋아요.
- 전체 재작성이나 요청 범위 밖의 추상화는 필요하지 않아요.

## 12. 데이터 안전과 문서에서 꼭 바로잡을 문제

### 12-1. README의 `DB 파일 삭제 = 캐시 비우기` 안내는 위험해요

현재 README는 캐시를 비우려면 `data/matchup_finder.db`를 삭제하라고 안내해요.
하지만 지금 이 파일에는 단순 경기 캐시만 있는 것이 아니에요.

- 관심 유저와 메모
- 앱 시작 자동 수집 설정
- 검색 인덱스
- 유저 등록 정보
- 수집 기록

도 함께 들어 있어요.

따라서 DB 파일을 지우면 “캐시만 비우는 것”이 아니라 사용자 설정과 기록도 같이 사라질 수 있어요.

#### 바라는 상태

- DB 전체 삭제를 가벼운 캐시 정리처럼 안내하면 안 돼요.
- 무엇이 삭제되는지 정확히 경고하고 백업·복구 범위를 알려줘야 해요.
- 단순 게임 정보 갱신과 사용자 데이터 초기화를 분리해 설명해야 해요.

### 12-2. 일반 DB 초기화 안의 테이블 삭제도 분리해야 해요

현재 스키마 초기화에는 일부 과거 수집 관련 테이블을 `DROP TABLE IF EXISTS`로 지우는 구문이 들어 있어요.
프로세스에서 `MatchCache`를 처음 만들 때 실행되는 일반 초기화에 삭제 작업이 섞여 있으면,
나중에 같은 이름의 데이터를 다시 쓰기 시작했을 때 조용히 사라질 수 있어요.
같은 초기화에서 과거 챌린저 발견 기록을 지우는 `DELETE`도 실행돼요.

#### 바라는 상태

- 테이블 삭제나 구조 변경은 일반 연결 초기화와 분리해야 해요.
- 한 번만 실행되는 버전 있는 변경으로 관리하고, 삭제 대상과 이유를 검증할 수 있어야 해요.

### 12-3. 과거 계획서는 역사 문서라는 표시가 필요해요

기존 문서에는 현재 코드와 다른 전제가 남아 있어요.

- 초기 문서는 React/FastAPI를 쓰지 않는다고 설명해요.
- 과거 DB 재설계 문서는 지금 사라진 챌린저 수집을 중심으로 설명해요.
- React/FastAPI 계획은 서버 재시작 시 job 소실을 허용된 조건으로 봤어요.
- README의 상세 기획 링크는 현재 `docs/2608/`로 옮겨진 경로와 맞지 않아요.

#### 바라는 상태

- 과거 문서는 삭제하지 말고 `역사 문서`라고 표시하는 것이 좋아요.
- 현재 제품 설명과 실제 호출 흐름을 담은 문서를 새 기준 문서로 삼아야 해요.
- 이 검토서도 실제 구현이 끝나면 결과에 맞게 갱신해야 해요.

## 13. 현재 테스트에서 비어 있는 부분

현재 자동 테스트는 자동 수집 기간 판단과 챔피언 이름 충돌 중심으로 9개이고,
프런트에는 테스트 명령이 없어요.

아래 행동은 아직 자동으로 지켜준다는 증거가 부족해요.

- 앱 첫 화면에서 메모 목록을 한 번만 요청하는지
- 같은 수집 버튼을 연속으로 눌러도 작업이 하나인지
- 서로 다른 작업이 같은 Match ID 상세를 한 번만 받는지
- 사람별 일부 실패가 다른 사람 수집을 망치지 않는지
- 상세 저장이 끝난 뒤에만 마지막 성공 시각이 바뀌는지
- 브라우저 F5 뒤에 진행 중 작업을 다시 찾는지
- 서버 재시작과 잠깐의 연결 끊김을 다르게 보여주는지
- DB 조회가 약속한 범위에서 로컬만 사용하는지
- API 호출 수가 실제 HTTP 요청과 맞는지
- 늦게 끝난 옛 DB 조회가 새 결과를 덮지 않는지
- 화면 결과와 CSV가 같은 적용 조건을 사용하는지
- 상세 탭이 필요한 데이터만 요청하는지

이 검토서에서는 어떤 테스트 도구를 쓸지 정하지 않아요.
구현 뒤 위 상황에서 **사용자에게 무엇이 보여야 하고 어떤 데이터가 남아야 하는지**를 검증하면 돼요.

## 15. 구현 뒤 사용자가 체감해야 할 완료 모습

아래 문장에 모두 `예`라고 답할 수 있으면 흐름 정리가 제대로 된 것이에요.

1. 앱을 열면 지금 게임 정보를 확인하는지, 자동 수집 중인지, 이미 최신이라 건너뛰었는지 보여요.
2. 첫 사용자라 데이터가 없으면 `한 명 바로 검색` 또는 `관심 유저 등록 → 첫 수집 → 조회` 중
   목적에 맞는 시작 방법을 알려줘요.
3. 관심 유저마다 마지막 완전 수집 시각과 수집 필요 여부를 볼 수 있어요.
4. 한 명 검색, 여러 명 수집, 자동 수집이 같은 진행 상태와 같은 성공 기준을 사용해요.
5. 같은 범위의 수집을 두 번 눌러도 같은 무거운 작업이 두 개 생기지 않아요.
6. 다른 메뉴로 이동해도 전체 작업 진행 상태를 볼 수 있어요.
7. F5를 눌러도 같은 서버에서 돌던 작업을 다시 찾아 이어서 보여줘요.
8. 서버가 재시작된 경우에는 `중단됨`과 이미 저장된 범위를 정확히 알려줘요.
9. 잠깐 통신이 끊겨도 서버 작업이 계속되는지 알려주고 다시 연결해요.
10. `저장된 매치업 조회`가 외부 API를 쓰는 경우에는 실행 전에 알려줘요.
11. 수집이 끝나면 사이드바 DB 숫자와 관심 유저 상태도 바로 최신으로 바뀌어요.
12. 화면의 API·새 경기·성공 숫자가 실제 뜻과 맞아요.
13. 조건을 바꾼 뒤 조회하지 않으면 아직 적용되지 않았다고 보여줘요.
14. 화면 결과와 CSV는 항상 같은 조건을 사용해요.
15. 경기 상세는 필요한 정보만 가져오고, 외부 호출이 생길 수 있음을 알려줘요.
16. 결과에서 상대 Riot ID를 중복 없이 한 번에 복사할 수 있어요.
17. 관심 유저가 없음, 저장 경기 없음, 조건 결과 없음, 통신 실패를 서로 다르게 보여줘요.
18. README만 읽어도 DB 파일 삭제가 사용자 메모와 설정까지 지울 수 있다는 사실을 알아요.

## 17. 이 문서에서 정하지 않은 것

이 문서는 구현자가 나중에 안전하게 계획을 세울 수 있도록 문제와 목표만 정리했어요.
따라서 아래 내용은 일부러 확정하지 않았어요.

- 작업 기록을 어느 테이블이나 브라우저 저장소에 둘지
- 수집을 한 줄로 처리할지 제한된 수로 동시에 처리할지
- 서버 재시작 뒤 정확한 재개를 어느 깊이까지 지원할지
- DB 페이지 조회를 어떤 SQL 모양으로 바꿀지
- 화면 컴포넌트를 몇 파일로 나눌지
- 고티어만 인덱싱할지 관심 유저는 모두 인덱싱할지
- 첫 실행에서 자동 수집할지 사용자에게 한 번 확인받을지

이 선택들은 구현 단계에서 현재 데이터와 기존 사용 방식을 다시 확인해 결정하면 돼요.
다만 어떤 선택을 하더라도 다음 원칙은 지켜야 해요.

> 화면에 보이는 말, 실제 Riot API 호출, DB에 남은 상태가 서로 같은 뜻이어야 해요.
